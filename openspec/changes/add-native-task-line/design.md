## Context

动机见 `proposal.md`「Why」。本设计需要落进既有结构的约束有三条：

- **适配器这一维的语义是"一个方案"**（`adapters/base.py`：`tier` 区分裸写法/标准库/生态/被测），
  被测框架只有一个且为 `Tier.UNDER_TEST`；主矩阵的 96 单元由 `matrix.unit_specs` 展开、
  交叉点推导与透视表都建立在该语义上。
- **harness 已有"主矩阵之外的独立探查线"这一形态**：调度语义探查与四段归因都经
  `runner.run()` 的一个键输出、并在独立子进程内运行（`run_in_child`），报告各成章节。
- **读数纪律**（`openspec/specs/measurement-protocol`）：计时区间内 MUST NOT 有 I/O；
  为采集而包装的接缝 MUST 逐条声明；结论 MUST 依据可精确比较的量。

被测侧的事实（本设计据以定形）：

- 两个开关的唯一读取点都在双臂执行体：`adaptive:enabled` 见 `dual_arm_worker.py:131`，
  `native:enabled` 见 `dual_arm_worker.py:88`（构造期显式拒绝）。
- **决策粒度是 Worker 类名**：`policy.decide(type(self).__name__)`，统计也是按类名索引。
- 决策含按探索率的随机探索（`adaptive:exploration` 默认 0.05，随机源未播种）。
- 统计可通过公开接口读回：`BanditPolicy.snapshot()` → `类名 → 臂名 → {n, mean}`。
- 统计落盘由 `adaptive:statsPath` 控制，**默认空 = 不写任何文件**。
- 原生扩展（`zoo-framework-native`）不在 PyPI，主包 0.11.0 的产物是 `py3-none-any` + sdist；
  扩展源码在框架仓的 `native/` 子目录，maturin 构建，当前只注册一个任务。

## Goals / Non-Goals

**Goals:**

- 让「纯解释 / 原生 / 路由」三种执行形态在同一轮、同一驱动层级下可比，并给出规模分界结论。
- 在任何倍数被给出之前先证明两臂语义等价（可证伪的门禁）。
- 让该线的数据与主矩阵同源留档，从而进入版本间对比与三种输出格式、两种语言。

**Non-Goals:**

- 不改主矩阵 96 单元的编排、口径与既有数值；不把该线并入交叉点推导。
- 不发布原生扩展到任何包索引（本变更只在 CI 内从框架仓同 tag 构建）。
- 不测被测框架的开关对**派发内核**的影响（内核不读这两个键，此前已实测为零变化）。
- 不引入新的计时口径：端到端与执行体自报沿用主矩阵的既有定义。

## Decisions

**D1 落点：独立探查线，不改适配器这一维。**
经 `runner.run()` 新增一个键（与 `semantics` / `attribution` 并列）输出，在独立子进程内运行
（`run_in_child`），不进入 `matrix.unit_specs`。
*备选*：并入主矩阵当对照档位——被否，破坏"适配器 = 一个方案"的语义（三档都是被测框架自己），
并使 `Tier.UNDER_TEST` 唯一性与交叉点推导都需要特判；harness 之外另起脚本——被否，拿不到
对外证据。

**D2 驱动接缝：复用 zoo 档的驱动层级，只换执行体形态。**
仍以调度派发层（线程池模式 + 框架的结果响应器）驱动，`drive_level` 声明不变。
*理由*：层级不变，则"被测层级被声明"这条既有结论对该线继续成立，两个口径的层级可比。
*备选*：走 `Master` 完整运行循环——被否，其 1s 轮询会支配读数（既有适配器文档已实测该理由）；
另起一套驱动——被否，重复实现且层级声明要重写。

**D3 三种形态的定义。**

| 形态 | 执行体 | 决策开销 |
|---|---|---|
| 纯解释 | 双臂基类**不声明**原生任务名 → 走解释臂，零分支零锁（框架的关闭语义） | 无 |
| 原生 | 框架的原生任务执行体（直接执行原生任务） | 无 |
| 路由 | 双臂基类 + 启用路由 + 声明原生任务名 | 有（即被测对象） |

*备选*：以主矩阵 zoo 档的合成执行体充当纯解释基线——被否，合成执行体与真实任务不可比，
"加快了多少"会退化成两件不同的事。

**D4 决策粒度决定 Worker 类的划分：每个规模档位一个 Worker 类。**
框架按类名学习与统计，同一个类里的不同规模**共享一条统计**，因此单类混跑所有规模时，
路由不可能按规模分流（小帧会被大帧的收益拖去走原生臂，反而更慢）。故该线**每规模一个类**，
并在留档中记录类名与规模的对应。
*备选*：单类混跑——被否，见上；这也正是"打开开关重跑一遍"最可能的静默失败形态。

**D5 臂的选择与臂均值取自被测框架的公开统计快照，不加插桩。**
`BanditPolicy.snapshot()` 已给出逐类逐臂的 `{n, mean}`；该线的收敛结论与臂间对照据此得出。
*理由*：满足"计时区间内 MUST NOT 有 I/O"与"插桩接缝须声明"（本设计为零新增接缝）。
*备选*：本仓的执行体子类覆盖框架受保护的计时入口自行记录——被否，引入额外接缝、并介入框架
内部时序，使"测得的是框架还是插桩"说不清。

**D6 统计持久化 MUST 保持关闭（`adaptive:statsPath` 留空）。**
默认空即不写文件、也不读文件；一旦配置路径，首次取决策器时会**读盘**（`get_bandit_policy`
→ `_restore_from_store().load()`），而取决策器发生在 worker 构造期（计时区间内）；
且跨测量单元的残留统计会成为先验，"这一轮学到什么"不再只由这一轮决定。
*实测补充（2026-10-11）*：配上该路径**并不会落盘**——框架内没有任何 `flush_stats` 调用点，
故"落盘落在计时区间内"这一理由不成立；切断该路径的依据是**读盘时点**与**先验污染**两条。
据此，本仓的断言落在配置层（该线不得声明该路径），文件新增与否只作旁证。
*备选*：配置路径以便跨进程累积——被否，见上。

**D13 配置只在"框架首次 import 时 CWD 有 config.json"这一条件下生效，故该线自带配置目录并先切目录。**
`_resolve` 内以默认路径构造 `ParamsFactory()`，因此参数类在**首次 import 时**就把
`./config.json` 的值解析成字面量；此后同进程再写配置无效（`AdaptiveParams.ADAPTIVE_ENABLED`
仍是 false）。实测：同进程先 import 框架再写配置，路由形态静默退化为纯解释形态、统计快照为空。
因此该线的子进程 MUST 先建配置目录、`chdir` 后再 import 框架。
*备选*：直接改参数类的类属性——被否，那不是"配置"，开关组合就不可复现也不可留档；
走 `Master` 完整运行循环——被否（见 D2），且仍不解决时序。
*推论*：该线不能塞进 `zoo_bench.worker` 既有 kind 分发（那里在模块级 `import` 了适配器，
框架已被 import），故它自成入口模块，由 runner 以独立子进程调起（详见 D10 的留档形态）。

**D7 本仓自带 Python 参照实现 + 语义等价性门禁。**
门禁输入覆盖正常帧、受控失败帧（功能码不支持 / 帧结构不一致）与坏 CRC 帧三类，两臂输出逐字节
比对；不通过则不出数字。
*备选*：取框架仓 `native/reference/` 的源码——被否，依赖框架仓的文件布局（非发布接口），
且该子目录不随包分发。

**D8 档位 = 任务规模，取框架自身工作包络的两端。**
1 寄存器（7 字节）/ 8 寄存器（21 字节）/ 125 寄存器（255 字节，输入上限内的最大合法帧），
三档；并发度沿用既有档位。
*依据*：框架公开的包络结论是"7 字节帧不划算、≥21 字节划算"，故该线自带一个**可证伪的预期**
（小帧应被路由到解释侧、大帧应在原生侧占优）；预期不成立时按规格如实报告。
*实测校准（2026-10-11，600 样本/形态/档）*：worker 口径下纯解释 / 原生 / 路由 三形态中位耗时
为 7 B 8.9 / 17.1 / 22.4 µs、21 B 15.8 / 17.4 / 32.6 µs、255 B 150.1 / 30.3 / 60.5 µs——
**分界落在 21 B 与 255 B 之间**（21 B 档原生并不更快），路由形态在该档位也确实只选了 python 臂；
255 B 档路由形态收敛到原生臂（逐臂次数 578/22）。框架自述的"≥21 字节划算"是**解析口径**，
本线是 **worker 口径**（含契约查找与输入输出转换约 15 µs 固定开销），报告按本线实测分界。
*读数限制*：这组中位数取自逐格一进程的那一版（见 D14），小规模档的形态差落在进程间漂移之内、
不可当结论；分界结论由 D14 的配对差复核（21 B 档的配对差不跨零即"原生更快"不成立，255 B 档
跨零方向相反）。
*备选*：沿用合成耗时档位——被否，回答不了"什么规模划算"。

**D9 扩展的获取：CI 从框架仓同 tag 的子目录直装。**
`pip install "zoo-framework-native @ git+<框架仓>@<与被测同名 tag>#subdirectory=native"`，
maturin 构建后端；来源（仓库、tag、子目录）与扩展自身版本进留档。
*备选*：先发布到包索引——被否（本次不新增发布面）；只用本机已构建的产物——被否，CI 不可复现。

**D10 留档：写进同一份按版本留档的原始数据。**
新增一个与主矩阵、语义、归因并列的键，使"同一份留档重渲染"与"版本间对比覆盖该维度"两条
既有要求自动成立。
*备选*：单独文件——被否，重渲染要读两处、版本对比要特判。

**D11 该线的状态取三态，且只有"本该能测却失败"才算失败。**
`ok` / `not_applicable`（该被测版本不具备该能力，附原因）/ `failed`（附原因）。三态都必须
在三种输出与两种语言中有文案。
*理由*：规格要求"能力缺失 MUST 明确示人、MUST NOT 静默省略"；把"不具备"与"失败"混为一谈会
让旧版本测量持续报假红。

**D12 该线失败不扩散到主矩阵与其他版本。**
`failed` 时该线维度如实示人、不出任何数字，但**不**导致其余版本与主矩阵的测量与发布被跳过；
CI 在摘要中以告警注释显式列出（避免"永远失败没人管"）。
*备选*：与既有的"自检失败阻止报告发布"同强度扩散——被否，一条线的失败会掩盖其他版本的可信
数据；2026-10-10 那次 CI 已出现过这种形态的代价（一个版本的档位噪声挡掉整轮归档与发布）。

**D14 一个并发度一个子进程，三形态在进程内逐轮交替（配对差）；关闭态不缺席。**
规格要求「参与对照的两侧来自同一次运行的同一次采样，MUST NOT 由两次运行的结果相减得出」。据此把
采样粒度从"一格一进程"改为"一个并发度一进程"：进程内每个周期把全部 (形态, 规模) 组合各跑一轮、
周期顺序逐轮翻转（ABBA），同规模的两形态对照取**同周期内的配对差**——其 p25/p75 不跨零即这份
口径分辨得出先后，跨零即如实报"分不出"；分界点与"划算臂"都由它给出，两侧各自的四分位区间不再
充当判据。
*实测依据（2026-10-11，同进程同池的交替 A/B 探针，120 对/档）*：逐格一进程时同形态相邻两格的
中位数实测可差约 100 µs，而 21 字节档上两形态配对差的中位数是 -1 µs（IQR −37…+33 µs）——
逐格一进程的两次运行曾据此给出"原生更快约 98 µs"的假结论，还连累"一致层"报出过一次不存在的
分歧；255 字节档的配对差是 +137 µs（IQR 87…187 µs），那一档的优势是真的。故判据取配对差，
**不取两侧各自的四分位区间**（后者只含各自窗口内的离散，不含窗口之间的漂移）。
*推论一（关闭语义核验的时点）*：三形态共处一进程后"跑完快照整个为空"不可能对整轮成立（路由形态
记账是它的预期行为），故该核验前移到**路由形态第一次执行之前**（先跑两个不记账的形态，再核验整个
快照为空），覆盖面是 预热轮数 × 并发度 × 不记账形态数 的提交；跑完后另逐类核验"不记账的形态
MUST NOT 留下类目"。路由形态自身处于关闭态时核验时点记为"跑完之后"（那时快照本就该空）。
*推论二（关闭态）*：原生开关为假时框架在**构造期**就拒绝（声明了原生臂而原生未启用，不许静默回退
解释臂），故该形态不去跑一次必然失败的构造，而是以 `status: "closed"` 带原因在场、不给数字；
它**不抑制**对照（规格：开关处于关闭状态本身 MUST NOT 让整线缺席）——"划算"层照常由纯解释与原生
两形态的配对样本给出，收敛/一致两层如实报"关着"而不是"样本太少"（后者会把读者引向"再多跑几轮"）。
*备选*：保持逐格一进程、只把判据换成配对差——被否，配对样本根本不在一个进程里；用容差阈值代替
分辨力判据——被否，规格明令禁止"落在区间内就算平"。

## Risks / Trade-offs

- [CI 环境未必自带 Rust 工具链] → 任务里先验证 `cargo`/`maturin` 可用；不可用则加一步
  rustup 安装。扩展编译只在测量前发生，**不进计时区间**。
- [扩展编译失败会让该版本该线 `failed`] → 取数照 D11/D12：不扩散、如实示人；并用一次
  `0.11.0` 的实跑确认该线能出数后才依赖它。
- [路由形态含探索率的随机性，逐臂次数逐轮波动] → 收敛判据按"优势臂占比显著高于探索率"复算，
  探索率随留档给出（规格已要求）；留档保留逐轮原始样本。
- [等价性门禁的输入集若不够真实，门禁会形同虚设] → 输入集必须含三类（正常/受控失败/坏 CRC），
  并由本仓自带的参照实现生成，规格已固定这一点。
- [两条线混读的风险（把真实任务对照读成派发开销对照）] → 报告该维度开头声明口径与局限
  （既有"口径的局限被声明"要求的落点），且该线数值不进主矩阵透视表与交叉点。

## Migration Plan

- **无数据迁移**：该线的键是新增键。旧留档缺该键时按"不适用/未探查"渲染（与语义维度"未复核"
  的既有先例同形），旧留档照旧可重新渲染；主矩阵数值一字不变。
- **回滚**：关闭该线的声明即回到现状——主矩阵、报告与发布流程都不依赖该线；已发布的留档仍可
  渲染（缺键走不适用分支）。
- **落地顺序**：先在本机把三形态与等价性门禁跑通并确认出数 → 再接 CI → 再扩报告三格式与两语言。

## Open Questions

- 上限规模取多少（扩展契约声明了输入上限，取该上限或其下一档即可）——不影响规格与任务拆分。
- 探索率取默认 0.05 还是显式设为 0（纯利用、便于读数）——规格只要求"随留档给出"，故可先按
  默认值跑一轮再定。
