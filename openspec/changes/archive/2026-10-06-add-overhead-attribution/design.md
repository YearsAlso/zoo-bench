## Context

动机见 `proposal.md`。本机实测（300 微秒档、并发 1 的中位）给出了这一维要回答的问题的样例：被测框架相对 `thread_pool` 超出 57 微秒落在提交侧、48 微秒落在回程，执行体那一段两者相同；提交侧内部 43.5 微秒落在 `execute_service` 的每轮序言，其中最大一块是每 worker 每轮三次配置查询（`ParamsFactory()` 构造 6.9 微秒/次）。同一批实测也否掉了一个常见猜测：框架热路径上的两次日志调用合共约 1 微秒/任务，只占总开销的 1-2%。

既有可复用的落点：「调度语义」维度已经跑通了"独立子进程探查 → 结论进结果结构 → 报告维度 → 块渲染"这一条路（`semantics.py` + `worker.py` 的 kind 分发 + `runner` 的收口 + `report.py` 的维度 + `render/blocks.py` 的块）。本变更与它同构。

## Goals / Non-Goals

**Goals**

- 报告能回答"被测框架相对各对照方案，多出来的那部分时间落在哪一段"
- 结论可复跑、可复核、随版本自动更新，且与既有维度同样进留档
- 插桩不改变被测对象（不改框架代码），且插桩自身的成本被量出来、可折价

**Non-Goals**

- 不做跨运行的归因对比（四段都是同一次运行内的相对量，与既有"绝对耗时不可跨运行比较"的口径一致）
- 不给对照方案做同层细分（它们的接缝不同，硬拆得到的层不可比）
- 不把开销高低做成门禁（只判"这份分解是否自洽"）
- 不覆盖全部单元（抽样固定的小集合；归因是诊断，不是主证据）
- 不给出"应该改成什么"的结论（那属于被测框架侧的判断）

## Decisions

### D1 · 四段的边界必须落在仪器能独立观测到的时刻

- **选**：**提交侧** = 调用适配器的提交入口到它返回；**手交** = 提交返回到执行体真正开始；**执行体** = 执行体自报的耗时；**回程** = 执行体结束到排空返回。执行体的开始与结束由**执行体自己**打点。
- **理由**：四段如果不共享同一组边界，就会重叠或留空，于是"和 = 端到端"这条自洽判据从定义上就不可能成立。执行体的起止时刻只有它能给——这正是既有的"耗时要由执行体自报"那条契约的延伸。
- **代价**：参与归因的档位必须用带打点的执行体。它与测量路径共用同一份负载，只多两个 `perf_counter`（实测约 0.1 微秒/任务，远小于任何一段的差异）。

### D2 · 结论以对照为基准，逐段对照

- **选**：结论表述为"被测框架相对各对照方案的超出部分主要落在哪一段"。
- **理由**：没有对照的分解回答不了"为什么慢"——提交侧 67 微秒这个数字旁边没有 `thread_pool` 的 10 微秒，读者无法判断它算不算高。"超出部分落在哪"直接把注意力指到该动的地方。
- **已考虑的替代**：只报被测框架的四段（拒绝：读者没有参照物，数字无法解读）。

### D3 · 被测框架多拆一层，对照方案不拆；深度差异必须写明

- **选**：被测框架的提交侧再分为 `call_workers`、调度内核的登记、调度模型的派发、以及"每轮策略查询"；对照方案只给四段。
- **理由**：拆分的用途是"下一步动哪里"，而动被测框架才有意义；各对照方案的接缝不同，硬拆出来的层与层之间不可比，给了反而误导。
- **代价**：报告里两边的分解深度不同。必须写明"对照方案没有被拆是因为它们的结构不同，不是因为没有结构"，否则读者会以为对照方案是一个不可分的黑盒。

### D4 · 插桩在 harness 侧：包装接缝，不改框架；接缝逐条声明

- **选**：包装框架的公开与内部接缝（设 worker 列表、走一次调度轮、调度内核的登记、调度模型的派发），不改 `zoo_framework/` 的任何代码。
- **理由**：改被测框架等于把被测对象换成"改过的版本"，那是另一件事。包装是 harness 一直在做的事——完成信号的取得本身就是包装来的。
- **代价**：包装有观察者效应，且会挡掉内联优化。缓解：把插桩自身的成本**也量出来**（同档位跑一遍不插桩的），随结论发布，使读者能折价。这条与既有口径说明的做法一致（本档的完成信号开销计入其端到端，并写明方向对被测框架不利）。

### D5 · 只报告、不门禁；但自洽判据要判否

- **选**：四段之和与同一次运行实测的端到端 MUST 自洽，不自洽则该次归因标为不可信并给出原因；"开销高不高"不参与任何门禁。
- **理由**：开销高低是被测对象的事实，不是 harness 的错误——把它做成门禁等于因为被测框架慢而让 CI 红。而分解算错是 harness 的错误，必须拦下：一份拆错了的分解比不给更坏，因为它会把人指向错误的地方。
- **代价**：多一条失效路径（不自洽时该维度作废），但这是"宁可说不可信，也不给错结论"。

### D6 · 与「调度语义」维度同构：独立子进程 + 结果结构 + 报告维度 + 块渲染

- **选**：新增一个探查 kind，在独立子进程里跑，结论进结果结构（与 `semantics` 并列），报告模型里新增一个维度，渲染层新增一个块。
- **理由**：那条路已经验证过（子进程隔离、失败可诊断、三种输出同源）。两个维度在报告里结构一致，读者不必学两套读法。
- **代价**：每增加一个 kind 就多一份子进程编排；受影响的只是探查规模（见 D7）。

### D7 · 探查规模取固定小集合，不随矩阵膨胀

- **选**：默认取矩阵里最短的一档与一档长档位，各在最低并发度与一个中等并发度上跑；被测框架与参与归因的对照方案在同一批档位上量。
- **理由**：归因是**诊断**，不是主证据。它的价值在"指向哪一段"，覆盖全部单元会让 CI 时长成倍而结论不变。
- **代价**：读者看不到非抽样档位的分解。缓解：报告写明抽了哪些档位，使"没给"与"测了是零"分得开。

### D8 · 前置：按机器并行能力撤下无效的开销数字

- **选**：并发度超过同一次运行的机器并行能力（环境自述里的逻辑核数）的组，**不给**"框架开销"与据此得出的变化倍数；这些组的端到端、吞吐与执行体自报值照旧给出，并写明原因。判据取自环境自述，不硬编码阈值。
- **理由**：实测（CI runner，4 逻辑核，asyncio_pool / 并发 64 / 10000 微秒档）每任务端到端 10.5 毫秒，而执行体自报耗时中位 **106.5 毫秒**——超订下后者含被抢占的等待（约 10.6 倍），两者相减得 **−913.8%**。对比页上还能看到由它衍生的 `变化 1483.013x`。**这不是"开销偏高"的噪声，是一个没有意义的减式结果**，而它与本变更"解释开销花在哪"的目的直接冲突：一边印 −913.8%、一边说能解释它，读者无法判断该信哪句。
- **为什么既有的缓解盖不住**：既有口径讲的是"并发度超出容量时端到端含排队等待"（开销被**抬高**）；这里是自报值被抬高导致开销变**负**。而"受排队污染"那个标志按开销**增长倍数**算，此处各档位一起受影响、增长倍数≈1，于是一组都没被标出（核对过 0.7.1b0 的留档："未通过的组数: 0"）。
- **已考虑的替代**：**只补一句口径说明**（拒绝：数字照旧印，读者仍无从判断哪一行不能读）；**删除留档里的相关字段**（拒绝：被撤下的是"相减的结果"这一解释，执行体自报值与每任务端到端都是有效原始量，删了会毁掉复核能力）。
- **两个触发条件，缺一不可**：① **结构性**——并发度 > 同一次运行环境自述里的逻辑核数；② **证据性**——算出来的开销**为负**。前者提前挡住可预见的超订，后者捕捉前者漏掉的（容器 CPU 配额可能低于 runner 报的核数，那时 `cpu_count` 会高估真实并行能力）。开销为负不可能是合法结果——框架只会加时间不会减时间——所以它出现即是"两个量不可比"的直接证据。
- **代价**：高并发档位少了一列数字。接受的取舍——那一列本来就不是"开销"；而"把并发压到核数以上会怎样"这个问题，端到端与吞吐仍在场、足以回答。

## Risks / Trade-offs

**[插桩的观察者效应] → ** 包装会改变被包装路径的成本（挡掉内联、多一次调用）。缓解：把插桩自身的成本量出来随结论发布；且结论以**相对**对照的超出量表述，两边都受同样的插桩影响，差值里的插桩成分大部分相互抵消。

**[短档位的分段数值不可靠] → ** 几十微秒的窗口里，两级 `perf_counter` 与调度颗粒度都会显著影响分段。缓解：归因只在足够长的档位上取样（与既有"档位长度"那条判定线一致），短档位不给分解并说明原因。

**[「手交」段在不同方案里含义不同] → ** 池化方案的手交是"排队 + 唤醒"，每次新建线程的方案（`bare_thread`）还含线程创建，两者不可直接比较。缓解：这本身就是要在报告里显示的**事实**（它解释了为什么它比池化方案慢），故如实标注各方案各自的手交含义，而不是把它们抹平成同一个词。

**[结论被读成优化建议] → ** "超出落在每轮策略查询"很容易被读成"把那个查询缓存起来"，而缓存策略是不是正确、会不会破坏配置热更新，是框架侧的决定。缓解：结论只陈述"超出落在哪一段"与"该段的插桩接缝是什么"，MUST NOT 给出"应该改成 X"这类判断。

**[抽样档位与对照方案的档位必须一致] → ** 段与段只有在同档位、同并发度下才可比。缓解：自洽判据之外再加一条可比性判据——不同档位或不同并发度的段不得并列成一条结论。

**[细分各项之和会超过提交侧，原因尚未解释清楚] → ** 实测：三个接缝在区间上确实嵌套（用区间记录验证过父的起止包住子的起止），但各项**独立测量**之和会比调度轮的总量多出约 3%（例：各项合计 81.0 微秒对调度轮 71.7 微秒）。**这不是数据错误，也不该夹掉**：本变更的处理是把它当成"独立测量"如实发布，并在报告里给出超出量与"不要相加"的说明。**开口**：那个 3% 从哪来还没查清（可能与被抢占时的计时归属有关），查到之前不把细分冒充成一个划分。记在这里而不是留在记忆里。

**[一份拆错了的分解会把人指错] → ** 比"不给分解"更坏。缓解：四段之和与端到端的一致性判据，未通过即判该次归因不可信（D5）。

**[撤下高并发的开销会改变已发布报告的内容] → ** 同一份留档在新代码下渲染出来的数字与旧版不同（少了一列），而已发布的站点上还有旧版。缓解：这不是数据变了而是**解释**变了；在报告的口径章节与 README 里把"为什么这些组不给开销"写清楚，使新旧两份的差异可解释，而不是让人以为测量本身改了。

**[机器并行能力取自环境自述，可能高估] → ** 容器 CPU 配额可能低于 runner 报的核数，那时 `cpu_count` 会放行仍然超订的组。缓解：负值触发器（D8 的触发条件②）——开销为负不可能是合法结果，出现即判不可比，这条不依赖核数估计。
