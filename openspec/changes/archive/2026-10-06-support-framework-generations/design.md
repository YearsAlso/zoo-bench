## Context

动机见 `proposal.md`。以下差异均于 2026-10-04 实测确认：把 `zoo-framework==0.7.1b0` 装进环境后跑用例，13 条失败，逐条追到 API 差异上；差异的另一半读框架仓库 `dev` 分支的源码确认。

**两代派发面的差异**

| | 0.6.x | 0.7.x |
|---|---|---|
| 装配 | 构造后赋 `worker_mode` / `pool_size` / `resource_pool` | 构造参数 `BaseWaiter(model_name=..., pool_size=...)` |
| 设 worker 列表 | 赋 `waiter.workers`（可写属性） | 该属性只读；入口 `core.set_workers()` / `call_workers()` |
| 完成信号 | 反应器路径**是坏的**——`EventReactorManager.dispatch` 以 `reactor_name`（默认 `"default"`）为键查表，取不到返回空列表后调 `.execute`，**每次调用都抛** `AttributeError`。可用的只有 `worker_running_callback` 这个框架内部回调 | 反应器路径**已修**（`reactor_name=None`、`"default"` 视为不过滤）；另有公开的 `core.is_inflight(worker)` |
| 停机 | `__del__` 隐式关池 | 显式 `shutdown(wait=True)` |
| 结构 | `BaseWaiter` 自己持有在飞表与池 | `core: WorkerDispatchCore`（簿记 / 超时观测 / 单一结算收口 `settle`）+ `model: SchedulerModel`（`ThreadPoolModel` / `ThreadPerTaskModel`） |

**这次实测暴露的判据是有效的**：design 里那条"追加版本必须重跑等价性用例"如实把问题拦下了。但本仓库同日还暴露了另一件事——**加版本的顺序被做反了**（先改矩阵、后装它跑用例），好在推送前发现，没有留下红的 CI。

**实测补充（2026-10-04，装上 0.7.1b0 跑全量之后）**：同一处耦合还有第二个落点——`src/zoo_bench/semantics.py` 的语义探查复制了同一套上一代驱动写法，在 0.7.x 上抛 `AttributeError`，使"调度语义的代价"整块记为探查失败。同时实测到两代的语义接线都变过：

| | 上一代 | 当前代 |
|---|---|---|
| 派发层超时 | 判定存在但取消/摘除动作整段是注释（`base_waiter.worker_band`） | `dispatch_core.reap_timeout` 记录 + 标不健康 + **摘在飞登记**，但不终止执行中的线程 |
| 事件层反应器入口 | `EventWorker` 调 `reactor.perform`（`EventReactor` 无此方法） | `EventWorker` 调 `reactor.execute`（存在） |

实测数据（0.7.1b0，`run_timeout=0.01s`，执行体 0.15s）：按调度轮反复驱动时摘除时刻 **0.0108s**（超时生效）；只派发一轮则 0.1515s（非循环 worker 首轮后即离开调度列表，判定不再有对象）。

## Goals / Non-Goals

**Goals**

- 让适配器同时驱动 0.6.x 与 0.7.x，使 `zoo-bench compare 0.6.0 0.7.1b0` 这类跨版本提升报告有对象
- 世代判定经得起版本号字符串的不可靠（实测两处写法不一致）
- 驱动不了时失败得清楚，而不是安静地测错东西
- 语义维度的探查在每一个声明的世代上都跑得起来，且它的结论不会跨代挪用

**Non-Goals**

- 不改 `zoo_framework/` 的任何代码
- 不为 0.7.x 新增对照方案（对照档位与本次无关）
- 不做世代 × 格式的组合爆炸；只做清单里实际声明的世代
- 不把"支持未来世代"写成承诺——未来世代的适配是未来的一次变更
- **不在本次重新推导事件层（优先级 / 重试）的逐项结论**：本次只保证它不被跨代挪用（见 D7）

## Decisions

### D1 · 一个适配器内部分流，而不是两个适配器

- **选**：`zoo.py` 内部按探测结果选择驱动路径，对外仍是**同一个**适配器标识与同一份契约实现。
- **理由**：报告与对比的语义是"被测框架"这一个主体，它跨版本存在。拆成 `zoo-0.6` / `zoo-0.7` 两个适配器会让"被测对象"这个概念分裂，`compare` 与交叉点结论都要跟着改；而分流只需在四个方法内部各选一条路。
- **已考虑的替代**：两个适配器 + 清单里分别声明。拒绝理由：那等于承认"被测对象随版本换了名字"，与 `subject_name()` 靠 `tier=under_test` 识别被测对象的既有设计冲突。

### D2 · 世代判定靠能力探测，不靠版本号

- **选**：判定"属于哪个世代"看的是**能力存在性与形态**——属性可写吗？`core.set_workers` 在吗？`worker_running_callback` 在吗？构造参数接受 `model_name` 吗？
- **理由**：版本号字符串实测不可靠（`0.7.1b0` 的轮子元数据里写的是 `0.7.1-beta`），而且未来世代的版本号我们无法预知。能力探测对"未知的将来世代"也能给出**正确的失败**（探测结果不匹配 → 明确报错），版本号比较则只会猜。
- **代价**：探测逻辑本身要维护。接受的取舍——探测失败是可见的（明确报错），版本号猜错是静默的。

### D3 · 完成信号按世代各用一种机制，且**优先用框架自己的**

- **选**：0.7.x 用框架的结果反应器（该版本已修好 dispatch）；0.6.x 只能拦 `worker_running_callback`（其反应器路径是坏的）。
- **理由**：完成信号是这条链路上最关键的观测点——它决定"端到端"从哪里结束。能走框架自己的投递路径时就走它（那是真实使用形态的一部分），走不通时才退回拦截内部回调（并说明为什么）。0.7.x 同时提供公开的 `core.is_inflight()`，可作为兜底与交叉验证。
- **代价**：两代各一条路径，测试要覆盖两代。本机只能装一个版本，故**两代的验证靠"同一套用例在两种环境下各跑一遍"**，而不是同一次运行里同时验证——这一点要在 tasks 里明确。

### D4 · 池尺寸走构造参数、停机走显式调用

- **选**：0.7.x 用 `BaseWaiter(model_name="thread_pool", pool_size=N)` 装配，测量结束调 `shutdown(wait=True)`；0.6.x 维持构造后赋值与既有的收尾方式。
- **理由**：0.7.x 把池与模式的所有权收进了 waiter（`model` 承担并发原语与容器生命周期），从外部赋 `resource_pool` 已不可能；而它的 `shutdown` 是显式动作且"可重复调用"，比 0.6.x 依赖 `__del__` 更可靠——顺带修掉了 0.6.x 路径上"池何时被关"的不确定性。

### D5 · 清单加回版本时，先装它跑用例，再改清单

- **选**：把这条顺序纪律写进 tasks 与 matrix.yaml 的注释：**先安装目标版本、重跑全套用例、通过后才改 `matrix.yaml`**。
- **理由**：本仓库同日刚吃过反着做的代价（先改清单、后装版本），而 design 里早就写着"追加版本必须重跑等价性用例"。纪律要写在会被读到的地方，而不是留在记忆里。

### D6 · 世代判定独立成模块，不塞在适配器里

- **选**：能力探测与世代标识放进 `src/zoo_bench/generations.py`，适配器、环境自述、语义探查三处共用。
- **理由**：实施中它被第三处需要——`environment.py` 要在自述里记"这次按哪一代驱动"，`semantics.py` 要按世代分流。把这份知识留在 `adapters/zoo.py` 内部，会让两个与适配器无关的模块反向依赖一个适配器模块（实施中已经这样写了一版，抽出来才顺）。**"装着的框架提供哪一代驱动面"是关于被测对象的事实，不是适配器的私事。**
- **已考虑的替代**：`environment` / `semantics` 直接 `from .adapters.zoo import probe_drive_generation`。拒绝理由：那不是依赖方向的问题而是归属问题——被测对象的标识不该由某个适配器模块定义。

### D7 · 语义探查按世代分流；结论带"在哪一代上得出"

- **选**：
  1. **派发层**（超时是否真的生效）改成**行为探查**，并在两代各自装配后驱动。驱动方式必须**按调度轮反复走**、且探查 worker 要声明循环——超时判定是调度轮的副产物，只派发一轮的话两代都不会摘除，量到的成了"执行体自己跑了多久"。
  2. **事件层**（优先级 / 重试）保持结构探查，但结论**按世代限定**：带着"在哪一代上得出"出场，装上的是另一代时标为未复核。
- **理由**：派发层的答案在运行时才成立（实测当前代 0.0108s 摘除、上一代 0.15s 不摘），必须实跑；而实测两代的事件层接线也变过（`perform` → `execute`），照抄上一代的坐标等于在报告里断言一个不存在的版本。**"没复核"与"复核过、结论是 X"是两条不同的信息，混在一起读者分不出来。**
- **代价**：事件层的两项在当前代标为未复核，报告里会看到两个"未复核"的条目。接受的取舍——重新推导它们需要单独一次探查设计（每项要有干净的开/关态才谈得上"定价"），那是一次独立变更；本次先保证不产生错误断言。

### D8 · 等价性判据改由返回值承载身份（本次顺带修掉的既有缺陷）

- **选**：执行体的身份从"自报耗时落在哪个槽位"改为**返回值本身**——每个执行体返回一个唯一标记，判据比较"条数 + 返回值多重集精确相等"。执行体仍睡一小段，但那只是为了保持并发，不承担身份。
- **理由**：实测（12 路并发、360 样本）墙钟超发有一个**绝对量级**的尾部——中位 +1ms，但 p95 约 +25ms、最坏 +77ms，**且不随睡眠时长缩放**（5ms 档与 50ms 档的 p95 几乎一样）。故"按耗时落点匹配"这道门禁约 15% 的跑随机判否，而判否的是"未通过等价性验证"——一道会随机变红的门禁很快会被学会忽略。**加宽槽位间距不是解法**：要容下 77ms 的尾部需把容差提到 40ms 以上、槽位 >160ms，比试一次跑到秒级，而最坏情况仍会漏。根因是判据落在墙钟上，不是容差不够。
- **为什么这次一并修**：它挡住了本次变更自己的验收——0.7.1b0 加进清单后，一次三目标的矩阵跑有很高概率撞上它，"三个目标自检全部通过"于是不可达成。加上**判据变强**（多重集精确相等比"落在区间里"更有鉴别力：丢弃、重复、张冠李戴三种错都判否），收益方向与本变更一致。
- **已考虑的替代**：**加宽容忍度**（30 行）——按上面的数据不成立，已排除；**换用共享账本**（最早的做法）——文件账本在 Windows 上因 `O_APPEND` 非原子而不可靠，已有实测记录；**把标记走 side-channel**——需要改适配器契约的返回形状，收益与"返回值即标记"相同，故不做。
- **代价**：等价性验证不再顺带证明"执行体的自报耗时能被回传"。接受的取舍——那条已由测量路径的档位偏差自检（`body_deviation_check`）覆盖，而两者本就是两件事。


## Risks / Trade-offs

**[0.7.x 的完成信号在真实运行中不可靠] → ** 反应器路径虽已修好，但若它在某种情况下不触发（例如反应器绑定时机），测量会等到 `drain` 超时而不产出数字，表现为该单元失败而非错误数字。缓解：`drain` 的超时是显式的（`DRAIN_TIMEOUT_SECONDS`），失败会带上下文；tasks 中要求对 0.7.x 额外用 `core.is_inflight()` 交叉验证一次完成判定。

**[本机只能装一个框架版本，两代验证无法同时进行] → ** 缓解：验证拆成两轮——装 0.6.0 跑一遍全绿、装 0.7.1b0 再跑一遍全绿，两轮的通过都记进 tasks 的证据里；CI 侧则由矩阵逐版本安装天然覆盖两代。

**[能力探测在未知世代上可能误判] → ** 某个未来世代可能"碰巧"具备被探测的能力但语义已变。缓解：探测不只查存在性，还校验形态（例如构造参数是否真的被接受、回调是否真的被调用）；且每个被测单元都过等价性验证，误判若导致行为错误会被它拦下。

**[0.7.x 与 0.6.x 的内存/资源生命周期不同] → ** 0.6.x 靠 `__del__`，若测量中途异常可能留下未关闭的池。缓解：本次把 0.6.x 路径的收尾也改为显式调用（其 `__del__` 已是兜底），并在测量单元的 `finally` 里保证执行。

**[跨版本对比的口径] → ** 0.6.0 的留档来自 CI 的既有运行，0.7.1b0 将是新运行。缓解：对比只比**同运行内的相对量**（既有设计），不绝对耗时，故两次运行不同批次不构成问题；报告里两侧的环境自述各自在场。

**[语义探查的驱动方式改了，0.6.x 的旧结论可能被推翻] → ** 派发层从"只派发一轮"改成"按调度轮反复驱动"——这是**方法上的修正**，不是回归：旧方法量的是执行体自己跑了多久。若 0.6.x 在新方法下的结论与已归档报告里的不一致，那是旧结论错了，须一并更正并说明，MUST NOT 让两处并存。

**[事件层的两项结论在当前代标为未复核] → ** 这是刻意的：照抄上一代的坐标比"未复核"坏得多（前者是一条错误断言，后者是一条诚实的空白）。缓解：报告里给出"未复核"的原因与"在哪一代上得出"；重新推导列入后续变更，而不是在这次悄悄丢掉。一个已知的负面后果是 0.7.x 的语义维度只有一个可用项（超时），读者看得到它少，但看不到"少"被藏起来。

**[探查本身给被测框架加了负载] → ** 语义探查跑在独立子进程里、在测量单元之外（既有设计），但它会在同一台机器上先后运行。缓解：探查的规模是固定的小常数（一个 worker、一个执行体档位），且它的结论不进测量数字；矩阵里的并发度与档位不受它影响。

**[0.7.x 上"超时生效"的结论容易被读多] → ** 生效的是**观测与熔断**（记录、标不健康、摘除在飞登记、停止派发），**不是终止**仍在执行的 worker——CPython 无法安全中断线程。缓解：证据文本明写这一点，MUST NOT 让读者把"摘除了"读成"被杀掉了"。
