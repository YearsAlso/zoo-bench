## 1. 世代判定

- [x] 1.1 实现能力探测：对当前装着的被测框架判定它提供哪一代的驱动面；验证：装 0.6.0 时判定为上一代、装 0.7.1b0 时判定为当前代，两者的探测结果里逐项列出**探测了什么、结果如何**（可读，不是布尔值）
- [x] 1.2 确认探测**不读版本号字符串**；验证：把版本号扫成一串诱饵值（含索引里的 `0.7.1b0` 与元数据里的 `0.7.1-beta`），判定结果不变；另有一条源码级守卫挡住任何版本读取
- [x] 1.3 实现无法匹配任何世代时的明确失败；验证：用一个只提供部分能力的替身对象触发该路径，异常信息里含"探测了哪些能力、各自结果"，且适配器**不留下可驱动的状态**
- [x] 1.4 把探测结果记进报告的环境自述（"这次测量用的是哪个世代的驱动面"）；验证：报告的运行环境章节含该字段，且两个世代各自的值不同（实测 `previous` / `current`）
- [x] 1.5 世代判定抽成独立模块（`src/zoo_bench/generations.py`），供适配器、环境自述、语义探查三处共用；验证：三处都不再各自实现判定，且 `environment` 与 `semantics` 不再反向依赖适配器模块

## 2. 驱动分流

- [x] 2.1 装配分流：当前代走构造参数（`model_name` + `pool_size`），上一代维持构造后赋值；验证：两个世代各自装配成功，且当前代的池尺寸等于矩阵里声明的并发度
- [x] 2.2 设 worker 列表分流：当前代走 `call_workers()`，上一代走属性赋值；验证：两个世代各自能把 worker 送进派发，且**同名 worker 不互相覆盖**（注入固定名字后该用例 10 秒内变红，证明它有牙齿）
- [x] 2.3 完成信号分流：当前代用框架的结果响应器（`WaiterResultReactor.on_result`，不新增响应器），上一代拦截 `worker_running_callback`；验证：两代各自测出的端到端耗时与执行体自报耗时之差**非负**，且自报值确实是执行体量出来的
- [x] 2.4 当前代额外用调度内核的在飞表交叉验证完成判定；验证：收齐完成信号时在飞表必为空；注入一个"在飞表非空"的读数后该检查确实变红
- [x] 2.5 停机分流：当前代显式 `shutdown(wait=True)`，上一代显式关池并摘引用；验证：单元结束后没有残留线程（注入空 teardown 后该用例变红），且重复调用幂等

## 3. 语义探查按世代分流

**背景（实测）**：语义探查复制了上一代的驱动写法，在 0.7.x 上抛 `AttributeError`，使"调度语义的代价"整块记为探查失败。且两代的语义接线都变过，旧结论与坐标不能跨代挪用。

- [x] 3.1 派发层的超时探查改成行为探查并按世代装配；验证：两代各自跑出结论，当前代观测到按调度轮驱动时在 `run_timeout` 附近摘除（实测 0.0116s vs 执行体 0.15s）
- [x] 3.2 探查改为按调度轮反复驱动、探查 worker 声明循环；验证：注入"只派发一轮"后当前代结论从"生效"翻转为"不生效"，证明驱动方式是结论的一部分
- [x] 3.3 证据文本明写"生效的是观测与熔断、不是终止执行中的 worker"；验证：报告里该条证据含此限定
- [x] 3.4 事件层的结论带上"在哪一代上得出"；验证：装上与得出该结论不同的一代时，该两项标为**未复核**并说明原因，且不含另一代的坐标（有专测证明没有被照抄）
- [x] 3.5 语义探查在每一个声明的世代上都给出结论；验证：两代各自的 `probe_semantics()` 都返回结论态，当前代上有一项可用
- [x] 3.6 核对 0.6.x 在新探查方法下的结论；验证：结论与已归档报告一致（仍是"未生效"），但读数从"探查上限 0.6012s"改为真实的自然结束时刻 0.1521s——**旧读数是个假观测**，新方法把它修掉了

## 4. 等价性判据改由返回值承载身份

**背景（实测，既有缺陷）**：身份原先由"耗时落在哪个槽位"给出，而并发睡眠的超发有一个绝对量级的尾部（中位 +1ms、p95 约 +25ms、最坏 +77ms，**不随睡眠时长缩放**），使自检约 15% 的跑随机判否。

- [x] 4.1 执行体改用唯一返回值当身份，重叠时长只用来保持并发；验证：判据不含任何容差，且并发下的重叠仍然存在
- [x] 4.2 失败期限与判据解耦：违约的病症是"永远等不到"，故受影响的用例自带短的失败期限而不是挂起十分钟
- [x] 4.3 判据的鉴别力双向验证；验证：丢任务、重复执行两个反例都被判否；注入"去重集合比较"后重复执行那条变红——证明判据必须比多重集
- [x] 4.4 确认调度停顿不再影响判定；验证：注入 50ms 停顿后判定不变（旧判据会因此翻转），且全套 3/3、精简矩阵 6/6 干净（此前约 1/5 与 1/7 会红）

## 5. 两代各跑一轮验证

**顺序纪律（D5）**：先装版本跑用例，通过后才动 `matrix.yaml`。本仓库同日已吃过反着做的代价。

- [x] 5.1 装 `zoo-framework==0.6.0`，跑全套用例；验证：223 通过、4 跳过、0 失败
- [x] 5.2 装 `zoo-framework==0.7.1b0`，跑全套用例；验证：225 通过、2 跳过、0 失败，且**不再出现** `AttributeError: property 'workers' ... has no setter` 这类世代不匹配的错误
- [x] 5.3 两个版本各跑一次精简矩阵（含 `zoo` 档），比对两代的报告字段齐备；验证：两代各自产出可渲染的留档，顶层与单元字段逐项一致（`absolute` / `relative` / `checks` / `rounds`），样本数相同
- [x] 5.4 确认 0.7.x 下自检通过；验证：`self_check.ok` 为真，两条不判定线（并发度、档位长度）的判定口径与 0.6.0 一致
