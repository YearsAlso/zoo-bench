## Context

现状见 proposal.md 的 Why。设计上要接的接缝：渲染链路的入口是 `report.build_model` → `render.build_blocks` → 三个后端（`deck` / `markdown` / `pdf`）+ `charts.render_all`；站点侧另有 `compare`（对比页，读两份留档）与 `index`（站点首页，读站点目录 + 留档）。文案分散在这些模块里（`blocks.py` 96 处、`deck.py` 64、`report.py` 37、`semantics.py` 24、`compare.py` 21、`index.py` 18、`charts.py` 17、`environment.py` 15、`attribution.py` 12）。

两条硬约束值得先说清：**图表是图片**（一张图的轴标签只能是一种语言，页内切换对它无效），**deck 与 PDF 会被单独转发**（双语同页会让它们更难读、PDF 本来就得选定语言）。这两条决定了"每语言各出一份"是唯一能覆盖全链路的形态。

还有一处既有的坑要接住：导出前的字符白名单（`blocks.SAFE_NON_ASCII`）是**按字体覆盖逐字试出来**的——它的注释记着 SimHei 缺 `µ`、wqy-zenhei 缺减号。它服务的其实是**内嵌字体的产物**（PDF、图表），对 HTML 无意义。

## Goals / Non-Goals

**Goals:**

- 同一份留档同时产出中英两份完整站点，英文在根、中文在 `zh/`。
- 缺失译文会**大声失败**，而不是留白或混语言。
- 英文产物的方框风险归零（ASCII 规则 + 用例），中文的既有字体门禁不变。

**Non-Goals:**

- 不做第三种语言、不做语言协商（`Accept-Language` 之类）——静态站点没有服务端。
- 不翻 `docs/` 与 `README`（那是框架仓库与本仓库的开发者文档，不是报告）。
- 不翻 CLI 输出与日志（本次范围是站点）。
- 不做旧链接重定向。

## Decisions

### D1 消息目录用纯 Python 表，不引 gettext/babel

一个模块 `zoo_bench/i18n.py`：`LANG_EN = "en"` / `LANG_ZH = "zh"`、`DEFAULT_LANG`（=英文，见 D3）、`t(key, lang, **params)`、以及键 → `{lang: 文案}` 的表。

**备选**：gettext `.po`（否决：新依赖 + 需编译 `.mo`，而这里只有几百条文案，且 `.po` 的键不是静态可查的）；JSON 文件（否决：键拼错只能在运行时发现，mypy 也帮不上）。

**键的形态**：点分命名（`blocks.section.environment`、`charts.axis.body_tier`），值用 `str.format` 模板承载数字（`"并发度 {concurrency}"`）。故 `report.py` 里那批 f-string 要改成模板 + 命名参数——这是本变更里最容易漏改的一类（f-string 前缀在，模板就没生效）。

### D2 `lang` 沿链路显式传递，模型里记下自己是用哪种语言建的

`build_model(result, *, lang)`、`build_blocks(model, charts, *, lang)`、`render_deck(model, blocks, *, lang)`、`render_pdf(..., lang)`、`render_all(..., lang)`、`render_site_index(..., lang)`、对比页同理。模型里存 `lang`，一供报告自述，二供下游断言一致。

**为什么不用全局状态**：本仓库为模块级全局吃过两次亏（`@cage` 的类名键、`ParamsFactory` 的进程级 `config_params`），且两种语言要在**同一次运行里各渲染一遍**——全局状态在多语言下就是一种次序依赖。

**代价**：模型随语言各建一次。它只做字典抽取与句子拼装，成本可忽略；而文案本来就在模型里（维度名、摘要句、口径局限），故这是必然而非取舍。

### D3 英文在根路径，中文在 `zh/`

`site/index.html`（英）+ `site/zh/index.html`（中），`site/<slug>/` 与 `site/compare-*/` 同理。选英文为主是因为这份报告的用途是**对外**选型举证。**这是 BREAKING**：根路径的内容会从中文变成英文（旧链接仍可访问，但会看到英文）。

**备选**：中文留根、英文放 `en/`（否决：与"对外举证"的用途相悖，且用户已明确选英文为主）；根路径放一个语言选择页（否决：多一跳、且"哪份是主"更含混）。

### D4 相对链接集中在一处算，并有"全站内部链接可达"的用例

语言切换链接在两个层级间跳（`zh/index.html` ↔ `../index.html`），首页卡片又要指向各语言的报告页。`assets.py` 的注释记着 `../style.css` 在相邻目录之间必然对不上的教训，故链接构造集中到一处函数（`i18n.document_href(...)` 一类），并由权威判据兜底：**遍历站点里所有 `<a href>`，逐个断言目标文件存在**（外链与 `#` 锚点排除）。

### D5 图表按语言各出一套，文件名带语言

图表是图片，标题与轴标签必须随语言；figure 文件按语言命名（如 `figures/en-overhead.svg` / `zh-overhead.svg`），**不能只按图名**——两种语言渲染到同一目录会互相覆盖，而覆盖后"看图的人不会发现这是另一语言的旧图"。用例钉住两种语言各自的 figure 都在场且互不覆盖。

### D6 英文字符规则：ASCII-only，且英文产物不要求中文字体

英文正文（含图表内文字）限制为 ASCII，导出前按语言选规则检查：中文走既有的 `SAFE_NON_ASCII` + CJK 范围，英文走 `text.isascii()`。违反时失败并**指出具体文本**——以便区分"漏了翻译"（该改目录）与"数据本身如此"（该单独处理）。

字体解析按语言分流：中文产物找不到中文字体则失败（既有行为不变）；**英文产物不因缺中文字体而失败**——否则 CI 装中文字体会变成英文产物的前置条件，而那并不是真的依赖。

### D7 一次调用出两种语言，CLI 签名与 CI 都不改

`zoo-bench render --framework X --out site/<slug>` 一次写出两份（根 + `zh/`），`index` / `compare` 同理。故 `bench.yml` 一行都不用改。

**备选**：加 `--lang` 只出一种（否决：CI 与本地都得记得调两次，漏一次就是"某种语言悄悄不更新"，而站点看起来仍然正常；若将来要裁剪，再加也不冲突）。

### D8 术语与单位表是翻译基准

微秒 → `microseconds`（不写 `µs`，见 D6）、任务/秒 → `tasks/s`、并发度 → `concurrency`、执行体档位 → `body tier`、被测框架 → `the framework under test`。表放在 `i18n.py` 顶部并作为目录注释，供后续新增文案遵循——术语漂移是双语报告最难被断言抓住的失败模式。

## Risks / Trade-offs

- **约 300 处迁移，漏一处英文页就残留中文** → 用例兜底：英文产物的正文里**不得出现 CJK 字符**（这条能抓住绝大多数漏网，因为中文文案几乎都含汉字）。
- **翻译质量无法用断言表达** → 只能用"键齐 / 无中文残留 / 两种语言数字一致"三条守住**结构性**正确；术语与措辞靠 D8 的表 + 人工复核。这一点如实记录，不假装有门禁。
- **模型与产物都翻倍** → 渲染时间与仓库体积各涨一份（站点目录多一份三件套）。实测一份报告约 2.6 MB 留档不变，站点增量在几百 KB 量级。
- **BREAKING：根路径内容变英文** → 已在 proposal 标注；不做重定向（静态站点没有这个机制，加一个跳转页会让"哪份是主"含混）。
- **首页/对比页的相对路径在两个语言层里易错** → D4 的那条"全站链接可达"用例是权威判据。
- **英文的 ASCII 规则可能撞上机器自述里的非 ASCII**（例如某台机器的 CPU 型号带中文）→ 导出失败并指出文本；这是刻意选的失败方向（宁可失败，不要方框），需要在报告里给出可执行的处置指引。
