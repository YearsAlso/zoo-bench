## Why

**报告现在能回答"慢多少"，不能回答"慢在哪"。** 它给出每个档位的框架开销占比与相对倍数，但没有一处能把那份开销拆开。想优化的人拿到数字之后，唯一能做的是回源码里猜。

猜测的代价已经实测出来了：把每任务端到端拆成四段之后（本机，300 微秒档、并发 1 的中位），被测框架相对 `thread_pool` 的差是这样分布的——

| 段 | zoo | thread_pool | 差 |
|---|---|---|---|
| 提交侧 | 67.6 微秒 | 10.5 | **+57** |
| 手交（提交→线程真开跑） | 23.8 | 9.3 | +14 |
| 执行体 | ~320 | ~315 | 0 |
| 回程（执行完→drain 返回） | 68.1 | 19.8 | **+48** |

再往下一层：提交侧那 67.6 微秒里，`call_workers` 只占 1.6、`begin` 2.6、`model.submit` 14.4，**剩下 43.5 微秒全在 `execute_service` 的每轮序言**——其中最大一块是 `ParamsFactory()` 构造（6.9 微秒/次 × 每个 worker 每轮 3 次：周期、相位、超时）。**这个结论从现有报告的任何一个数字里都看不出来**，而它正是"下一步该优化什么"的答案。

顺带一个反直觉的对照：框架热路径上那两次 `LogUtils.info`（`run()` 的 Start/Stop）实测 0.485 微秒/次、每任务合共约 1 微秒，**只占总开销的 1-2%**——不实测就会把它当成主要嫌疑。

**为什么现在做**：这一维的性质与既有的"调度语义"维度同构（独立子进程探查 + 报告维度 + 块渲染），那条路已经跑通、有现成的落点；而清单里现在有三个目标，"这一步优化到底有没有用"的问题会随每次版本变化反复出现。

## What Changes

- **报告新增一个维度：开销归因**。它在**同一档位、同一并发度**下同时量被测框架与各对照方案，把每任务端到端拆成四段并给出各段中位数：
  - **提交侧**：调用适配器的提交入口到它返回（适配器与框架在派发前的同步工作）
  - **手交**：提交返回到执行体真正开始（线程池排队 + 线程唤醒）
  - **执行体**：执行体自身的实测耗时
  - **回程**：执行体结束到 `drain` 返回（完成信号的取得与投递）
- **被测框架再拆一层**：把提交侧细分为 `call_workers`、调度内核的登记、调度模型的派发、以及 `execute_service` 里"每轮的策略查询"（周期/相位/超时各查一次配置）。
- **结论以"超出对照的部分落在哪一段"表述**，而不是只给一个总开销数字——读者要的是下一步动哪里。
- **插桩在 harness 侧**：不改 `zoo_framework/` 的任何代码（可包装框架的公开与内部接缝，凡用到的接缝都逐条声明在结论里）。
- **计时区间内不做任何 I/O**：逐任务的原始样本留在内存，只把聚合结果带回父进程。日志一类的东西不落盘，也就没有"插桩 I/O 污染被测数字"这条路。
- **自洽判据**：四段之和与同一次运行里实测的端到端必须一致（超出容差即判该次归因不可信），否则一份拆错了的分解比不给更坏。

## Capabilities

### New Capabilities

无。这一维是既有两个能力各自的延伸：**怎么量**属于测量协议，**报告里怎么呈现与如何下结论**属于报告能力。

### Modified Capabilities

- `measurement-protocol`：新增一条要求——开销归因的四段 MUST 在同一次运行、同一个进程内采集；计时区间内 MUST NOT 有任何 I/O（含日志落盘）；用到的插桩接缝 MUST 被声明；四段之和 MUST 与同一次运行实测的端到端自洽。
- `comparison-report`：新增一条要求——报告 MUST 含开销归因维度，且其结论 MUST 以"超出对照的部分落在哪一段"表述。该维度 MUST NOT 只给总开销。

## Impact

**受影响文件**

| 类别 | 文件 |
|---|---|
| 归因探查（新） | `src/zoo_bench/attribution.py`（四段采集 + 被测框架的一层细分 + 插桩接缝声明） |
| 探查入口 | `src/zoo_bench/worker.py`（新增一个 kind，与 `semantics`、`verify`、`measure` 并列） |
| 编排 | `src/zoo_bench/runner.py`（把探查结论收进结果结构，与 `semantics` 同一处） |
| 报告模型 | `src/zoo_bench/report.py`（新增维度；与 `semantics` 同构，缺省时如实标"未探查"） |
| 渲染 | `src/zoo_bench/render/blocks.py`（新维度的块） |
| 矩阵 | `matrix.yaml`（可选：声明参与归因的档位与并发度；缺省取矩阵里最短的一档与一档长档位） |
| 测试 | `tests/test_attribution.py`（新）、`tests/test_report_model.py`、`tests/test_render.py` |

**不涉及的边界**

- 不改 `zoo_framework/` 的任何代码
- 不做**跨运行**的归因对比：四段都是同一次运行内的相对量，与既有口径一致（绝对耗时仍不可跨运行比较）
- 不把归因数字做成门禁（自洽判据只判"这份分解是否可信"，不判"开销高不高"）——开销高低是结论，不是错误
- 不给对照方案做同层的细分：它们的段数与接缝不同，硬拆会得到不可比的数字。对照方案只给四段
- 不引入新的第三方依赖
