## 0. 前置：撤下无效的开销数字

**背景（CI 实测）**：4 逻辑核的 runner 上，asyncio_pool / 并发 64 / 10000 微秒档——每任务端到端 10.5 毫秒，执行体自报耗时中位 106.5 毫秒，相减得 **−913.8%**；对比页上有由它衍生的 `变化 1483.013x`。机制是超订下执行体自身的墙钟被抬高，与"墙钟 ÷ 并发度"不再可比。

- [x] 0.1 判据独立成模块（`caliber.py`），报告与对比共用；两个触发器都要有：并发度 > 同一次运行环境自述里的逻辑核数、以及算出来的开销为负；验证：两类触发各有正反例（`tests/test_caliber.py` 8 条），且判据里没有硬编码阈值——同一组数据换个核数即得不同判定
- [x] 0.2 报告模型撤下这些组的框架开销：开销维度把两个数字置为 `None`（留在模型里任何一个后端都可能顺手印出来）、交叉点也不给；验证：注入"并发 64 / 核数 4"的单元后该行无开销与交叉点，而执行体自报值仍在场
- [x] 0.3 跨版本对比同样处理：任一侧不可读则该行连两侧比值都不给（只给比值会让读者自己减出一个数）；验证：用 CI 的真实留档做对比，比值 >100 的行为 **0**，文本里不再出现 `1483`
- [x] 0.4 原始字段一个不删：验证：撤下只发生在报告模型层，留档里 `framework_overhead_seconds` 等字段一字未动（真实留档复核时仍能读出 −913.8% 背后的三个原始量）
- [x] 0.5 原因写进报告的口径章节（新增"不给出开销数字的组"并点名到组）、开销表上方的说明（"带 — 的行"当场解释，不让读者跨章节去猜）与 README 的已知成本章节
- [x] 0.6 用真实留档复核：取 CI 上那两份留档重新渲染——两份各撤下 18 个组、**仍被当作开销给出的负值为 0**、口径章节点名、对比页 "1483" 消失且带"不可读"说明。顺带确认被撤下的不止并发 64：并发 4（恰等于核数）与 16 的长档位也因**自报值被争用抬高**而判为负（如 thread_pool/4/10000：每任务 9.9ms 而自报 19.2ms），故那条证据性触发在容量边界上也在干活

## 1. 四段采集探针

- [x] 1.1 实现带打点的执行体（模块级、可 pickle，与测量路径共用 `run_iterations`）；迭代次数按**组**校准一次并复用——每个执行体各校一遍会让探查慢到不可用
- [x] 1.2 实现四段采集；验证：真实探查下逐任务自洽偏差 **0.00%**（另有纯逻辑用例逐段钉住它的两个时刻）
- [x] 1.3 计时区间内不做任何 I/O：逐任务样本留在内存，只交出聚合结果（模块文档写明这条纪律；插桩只做几次 `perf_counter` 与一次字典累加）
- [x] 1.4 新增 `attribution` kind（与 `verify`/`measure`/`semantics` 并列）；是否细分由适配器的 `tier` 决定，不由调用方传——少一处可传错的东西

## 2. 被测框架的细分与插桩成本

- [x] 2.1 包装框架接缝（调度轮 / 派发 / 三处策略解析），**不改框架代码**，退出时还原（含异常路径）；插桩成本由同一子进程里**配对**的两轮得到并随结论发布（实测约 16 微秒/任务，读者可折价）
- [x] 2.2 提交侧细分为四项；验证：**改成了「独立测量」而不是划分**——实测各项之和会比提交侧多出约 3%，原因尚未查清，故如实发布超出量并写明不要相加（见 design 的对应风险条目）
- [x] 2.3 接缝由插桩器**如实回报实际装上的那些**（不是照静态清单抄——实测踩过「同一项同时出现在用到与缺席两处」）；缺席的另列一条并说明这一代没有该入口
- [x] 2.4 细分只对被测框架做（由适配器自己的 `tier` 决定）；报告里细分单独成节

## 3. 编排与报告维度

- [x] 3.1 结论收进结果结构（与 `semantics` 并列）；单个组探查失败记为 `probe_failed` 并带上原因，不让整轮失败
- [x] 3.2 报告模型新增该维度；缺省时给未探查占位（与跑了但不可测分得开），有专测钉住五个维度都在场
- [x] 3.3 抽样固定：矩阵里最短与最长各一档 × 最低并发度与**不超过机器并行能力**的最大一档；报告写明抽样范围与核数。上界取核数是因为超订时那几段量到的是争用（与 D8 同一条判据）

- [x] 4.1 四段之和与端到端的一致性判据（**逐任务**比较，不用中位数相加——中位数不可加）；验证：注入一处漏算后该判据判否
