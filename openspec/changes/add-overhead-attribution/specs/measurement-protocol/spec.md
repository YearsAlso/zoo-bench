## ADDED Requirements

### Requirement: 开销归因的四段 MUST 在同一次运行内采集，且计时区间内 MUST NOT 有 I/O

开销归因 SHALL 把每个任务的端到端耗时拆成四段——**提交侧**（调用提交入口到它返回）、**手交**（提交返回到执行体真正开始）、**执行体**（执行体自身实测耗时）、**回程**（执行体结束到排空返回）。这四段 MUST 在同一次运行、同一个进程内、针对**同一批提交**采集，MUST NOT 由多次运行的结果拼接。计时区间内 MUST NOT 执行任何 I/O（含写文件、打印、日志落盘）：需要留下的证据 MUST 留在内存里，跑完再一次性交出。凡为采集而包装的框架接缝 MUST 被逐条声明。

#### Scenario: 四段来自同一批提交
- **WHEN** 读取某个档位与并发度下的归因结果
- **THEN** 四段由同一次运行、同一批提交得出，不是跨运行或跨批次拼起来的

#### Scenario: 计时区间内不发生 I/O
- **WHEN** 归因探查运行
- **THEN** 计时区间内没有写文件、打印或日志落盘，证据在内存中累积

#### Scenario: 用到的插桩接缝被声明
- **WHEN** 读取归因结论
- **THEN** 其中列出为采集而包装了框架的哪些入口，使读者能判断这份分解是按什么口径得到的

#### Scenario: 四段之和与端到端自洽
- **WHEN** 把某档位的四段之和与同一次运行里实测的端到端做比较
- **THEN** 二者一致；若超出容差，该次归因被标为不可信，MUST NOT 照常发布其结论

#### Scenario: 细分不改变总量
- **WHEN** 只看被测框架在提交侧内部的细分项
- **THEN** 这些细分项之和与提交侧那一段一致（在容差内），细分只重排、不新增也不吞掉时间
