## Why

**harness 现在只能驱动被测框架的一个世代。** 2026-10-04 实测：把 `zoo-framework==0.7.1b0` 装进环境后跑用例，**13 条当场失败**，首条就是

```
AttributeError: property 'workers' of 'BaseWaiter' object has no setter
```

zoo 适配器是按 0.6.x 的派发面写的（0.6.0 的 `BaseWaiter.workers` 是可写属性，适配器靠赋值驱动它）；0.7.x 把它改成了只读属性，替代入口是 `core.set_workers()` / `call_workers()`。此外 0.7.x 的 waiter 重构为 `core: WorkerDispatchCore` + `model: SchedulerModel` 的组合，池尺寸成了构造参数，停机成了显式动作，**而 0.6.x 上唯一可用的完成信号（拦截 `worker_running_callback`）在 0.7.x 的公开面上已不存在**。

这正是 design 里那条风险的实例——"适配器的驱动假设会随被测版本改变"，其缓解措施写着"往 matrix.yaml 追加版本时**必须重跑等价性用例**，它是'新版本下驱动仍然成立'的判据"。判据如实把问题拦下了，所以本次要做的不是改一处赋值，而是让适配器**按世代分流**。

**为什么必须两个世代并存**：这份 harness 的用途是"相对各对照方案，本框架快不快"——而"上一版 vs 这一版"正是读者最关心的对比。`matrix.yaml` 里同时存在 0.6.x 与 0.7.x，才能用 `zoo-bench compare` 回答"0.7 比 0.6 快了多少"。只留一个世代，跨版本提升报告就没有对象。

**实施中发现的第二处耦合与一个既有的门禁缺陷**（2026-10-04，装上 0.7.1b0 跑全量之后）：

- **同一处耦合还有第二个落点**：语义维度的探查（`src/zoo_bench/semantics.py`）复制了同一套上一代驱动写法，在 0.7.x 上直接抛 `AttributeError`，于是"调度语义的代价"这一整块对 0.7.x 记为探查失败——而它恰是被测框架最主要的差异化。同时实测发现两代在这一层的**接线也变过**：派发层上当前代的超时判定真的会摘表熔断（0.0108s 摘除，执行体 0.15s），上一代的取消/摘除动作整段是注释；事件层上当前代 `EventWorker` 已改成调 `reactor.execute`，不再是 `perform`。故本次一并把它按世代分流，并让结论带上"在哪一代上得出"——照抄旧坐标等于断言一个不存在的版本。
- **等价性判据依赖墙钟精度，约 15% 的跑随机判否**（既有缺陷，与世代无关）：身份原先由"耗时落在哪个槽位"给出，而实测并发睡眠的超发有一个**绝对量级**的尾部——中位 +1ms，但 p95 约 +25ms、最坏 +77ms，**且不随睡眠时长缩放**（5ms 档与 50ms 档的 p95 几乎一样）。故加宽槽位间距解决不了（要容下它得把容差提到 40ms 以上，最坏情况仍会漏）。改为**以返回值当身份**：判据变成"条数 + 返回值集合精确相等"，与负载无关，且比宽容差匹配更强。**这条缺陷挡住了本次变更自己的验收**——0.7.1b0 加进清单后，一次三目标的矩阵跑有很高概率撞上它，"三个目标自检全部通过"于是不可达成——故一并修掉。

## What Changes

- **世代判定抽成共用能力**：按**能力探测**（属性可写？回调存在？构造参数接受？）判定当前装着的一代。它在三处被需要——适配器（怎么驱动）、环境自述（这次是按哪一代驱动的）、语义探查（这一维在这一代能不能跑），故独立成模块，而不是塞在适配器内部
- **适配器按世代分流**：装配方式、设 worker 列表的入口、完成信号的取得、停机动作，四处都按被测版本选择实现，而不是二选一
- **完成信号按世代各用一种机制**：上一代只能拦框架内部回调（其反应器路径是坏的——`EventReactorManager.dispatch` 每次调用都抛 `AttributeError`）；当前代走框架自己的结果响应器（该版本已修好），并在收齐完成信号时用调度内核的在飞表交叉验证
- **语义维度的探查按世代分流，且结论按"在哪一代上得出"限定**：实测两代在这一层的接线都变过（派发层：当前代的超时判定真的会摘表熔断，上一代的取消/摘除动作整段是注释；事件层：当前代 `EventWorker` 已改成调 `reactor.execute`，不再是 `perform`）。在某一代上得出的结论与 `file:line` 坐标 MUST NOT 被当作另一代的事实报告出来
- **驱动不了就明确失败**：世代无法识别时抛可读的异常并说明探测了什么，而不是静默退回某个默认路径去测错东西
- **`matrix.yaml` 把 `0.7.1b0` 与框架 `dev` 分支加回清单**
- **等价性判据改为以返回值当身份**（`workloads/identity.py`）：不再用"耗时落在哪个槽位"判定
  "是不是同一个执行体"，改为执行体返回唯一标记、判据比较条数与返回值集合。墙钟只用于测量
  耗时本身，不再承担身份——它的尾部停顿不该决定门禁的红绿
- 未纳入的世代不再靠注释说明，而是由"能驱动哪些世代"的判定如实反映

## Capabilities

### New Capabilities

无。本次是既有能力的**要求变更**：适配器契约原先只隐含"驱动被测框架"，现在要明确"驱动矩阵里声明的每一个世代"；测量协议原先只要求自检口径、要求语义维度给出结论，现在要明确"版本相关的结论必须按版本限定"以及"判据不得依赖墙钟精度"。

### Modified Capabilities

- `adapter-contract`：新增两条要求——① 适配器 MUST 能驱动**矩阵里声明的每一个框架世代**，且世代判定 MUST 依据能力探测而非版本号字符串；② 世代无法驱动时 MUST 明确失败并指明探测到了什么，MUST NOT 静默退回默认路径。
- `measurement-protocol`：新增两条要求——① 语义维度的探查 MUST 能在清单声明的每一个世代上运行，且其结论 MUST 按世代限定，MUST NOT 把在某一代上得出的结论与坐标当成另一代的事实报告出来；② 自检与门禁的判据 MUST NOT 依赖墙钟精度，其结论必须与机器负载无关。

## Impact

**受影响文件**

| 类别 | 文件 |
|---|---|
| 世代判定（新） | `src/zoo_bench/generations.py`（三处共用：适配器 / 环境自述 / 语义探查） |
| 适配器 | `src/zoo_bench/adapters/zoo.py`（世代分流的主体） |
| 语义探查 | `src/zoo_bench/semantics.py`（派发层按世代分流；事件层结论按世代限定） |
| 等价性判据 | `src/zoo_bench/workloads/identity.py`、`src/zoo_bench/worker.py`（身份改由返回值承载） |
| 目标与矩阵 | `matrix.yaml`（加回三个条目） |
| 环境自述 | `src/zoo_bench/environment.py`、`src/zoo_bench/render/blocks.py`（报告里要能看出这次按哪一代驱动） |
| 测试 | `tests/test_framework_generations.py`（新）、`tests/test_semantics.py`、`tests/test_report_model.py` |

**不涉及的边界**

- 不改 `zoo_framework/` 的任何代码——被测框架的 API 变化是要适配的对象，不是要改的对象
- 不为 0.7.x 新增对照方案；对照档位（裸写法、标准库并发模型、同生态调度库）与本次无关
- 不做"世代矩阵"式的组合爆炸：只做 harness 目前在清单里声明的世代
- **事件层（优先级 / 重试）的逐项结论不在本次重新推导**：本次只保证它不被跨代挪用（装上另一代时标为未复核）。重新推导需要单独一次探查设计，见 design 的风险条目
- 不复活 `bench/`，不改它的结论
