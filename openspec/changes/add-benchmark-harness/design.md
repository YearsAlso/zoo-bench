## Context

动机见 `proposal.md`。以下现状来自框架仓库 `bench/` 的实测记录（Windows / Python 3.13，执行体耗时在同一次运行内埋点）。

**框架自身开销占比随执行体变长而下降**（开销本身基本恒定）：

| 档位 | Worker 体 | 端到端 | 框架开销 | 占比 |
|---|---|---|---|---|
| cpu-1x | 0.039 ms | 0.133 ms | 0.094 ms | **70.76%** |
| cpu-10x | 0.289 ms | 0.391 ms | 0.102 ms | **26.12%** |
| cpu-100x | 2.734 ms | 2.858 ms | 0.124 ms | **4.34%** |
| io-10ms | 10.332 ms | 10.551 ms | 0.219 ms | **2.08%** |

**被否决的对照方案**：`adopt-rust-core` 已实测最小 Tokio 派发器相对框架派发路径的加速比上限为 **1.67x**（典型 1.0–1.2x），结论 no-go。瓶颈在 GIL 与跨线程唤醒，不在调度实现。本变更**不重复论证该方向**，但把已测到的四项纯 Python 优化（12x–800x）作为未来版本的预期收益来源。

**测量方法上的既有教训**（`bench/README.md` 的三条硬约束，本设计的直接依据）：

1. 框架开销的 Linux 数字不可用——WSL2 的 Hypervisor 放大跨线程唤醒约 3 倍，开销虚高到 328–432 µs
2. 负载是替身不是真实 trace——`bench/workload.py` 只是形状近似，仓库内没有真实样本
3. 执行体耗时必须在同一次运行内埋点——用另一次测量的结果做减法会把开销高估一倍（`profile_framework.py` 第一版的实际故障）

## Goals / Non-Goals

**Goals**

- 让"框架快不快、相对谁快"成为可复跑、可比对、可对外引用的常设事实
- 给出**交叉点**而非单点加速比：任务短于多少用裸写法、长于多少用 zoo 的相对开销低于阈值
- 让每个框架版本的性能变化可查询，从而使既有四项纯 Python 优化有量化验收手段
- 测量口径经得起"你那台机器/那次运行"的质疑

**Non-Goals**

- 不追求硬实时或抖动有界，只要求抖动**可观测**（分位数 + 离散度）
- 不做分布式、持久化、broker 语义的对照（见 D3）
- 不把报告写回框架仓库（见 D9）
- 不改 `zoo_framework/` 的运行时行为与公开 API
- 不复活 `bench/`，不重复论证 Rust 方向

## Decisions

### D1 · 独立仓库，且框架侧不引用它的代码

- **选**：harness 与报告全部落在 `YearsAlso/zoo-bench`；框架仓库本地以 **gitignore 的并列目录**保留工作副本，**不用 submodule**。
- **理由**：框架仓库不需要 zoo-bench 的代码——zoo-bench 的 CI 是 `pip install zoo-framework==<版本>` 去测，跨版本对比也是装不同版本，框架侧只需要一个报告 URL。submodule 会建立一种"框架需要 bench"的假耦合，并带来两项实际摩擦：`pre-commit run --all-files` 会开始扫 zoo-bench 的文件（被框架的 ruff 与 format 规则管），贡献者不加 `--recursive` 会看到空目录。
- **已考虑的替代**：submodule。若将来需要"框架仓库里有一条机器可读的指向 harness 版本的指针"，再改为 submodule；当前该需求由报告的环境自述块（含被测版本与 commit sha）覆盖。

### D2 · 适配器是一等抽象，harness 不内建任何方案

- **选**：契约只含 `setup` / `submit` / `drain` / `teardown` 四个方法；三档内置实现是契约的**实现**而非 harness 的分支。
- **理由**：对照对象要能持续增加（使用者提出新的对照实现是完全预期的用法）。若 harness 内建分支，每加一个方案都要改核心；契约化后新增对照是纯增量。
- **验证要求**：新增一个对照实现不得修改 `runner.py`、`metrics.py`、`render/` 中任何文件。

### D3 · 同生态调度库分两层：`APScheduler` 默认跑，`Celery` 走可选依赖

- **选**：`APScheduler` 作为默认跑的同类对照；`Celery` 放入可选依赖，不进默认矩阵，且其数字在报告中单独标注"架构不同，不可直接对标"。
- **理由**：`Celery` 是分布式、需要 broker、带持久化投递语义的方案，与"进程内派发一个 callable 并收回完成信号"不是同一件事。放进同一张表会既是稻草人又是错误对照——赢了不代表 zoo 更好，输了也不代表 zoo 更差。放进可选依赖可以让有需要的读者自行取数，同时不污染默认报告的口径。
- **已考虑的替代**：完全不收录 `Celery`。拒绝理由：读者最可能拿它做对比，主动给出带标注的数字比让读者自行臆测更好。

### D4 · 每个适配器跑在独立子进程

- **选**：`runner` 为每个（适配器 × 档位 × 并发度）单元派生一个子进程，子进程内完成 warmup、重复与采样，只把结果回传父进程。
- **理由**：asyncio 的事件循环、gevent 的 monkey patch、`ProcessPoolExecutor` 的进程池都会与同一进程内的其他方案互相污染；同进程内对照得到的数字无法归因到被测方案。子进程隔离也让"某档崩溃"只损失该档数据而非整轮。
- **代价**：进程启动成本计入每单元固定开销，故每单元内部须做足重复次数，不能靠增加单元数堆样本。

### D5 · 执行体耗时在同一次运行内埋点

- **选**：执行体自身记录进入与退出时刻，随结果一并回传；框架开销 = 端到端耗时 − 同一次运行内测得的执行体耗时。
- **理由**：`bench/profile_framework.py` 第一版用另一次单独测量的执行体耗时做减法，把开销高估了一倍。两次运行之间的 CPU 频率、缓存状态与调度噪声不同，减法引入的是系统性偏差而非随机误差。
- **验证要求**：空执行体（耗时≈0）下测得的框架开销必须落在合理量级，且随执行体档位提升基本恒定——若随档位单调上升，说明埋点口径有误（把执行体成本漏算进了开销）。

### D6 · 两类数字，报告中不得混排

- **选**：报告明确区分并在排版上隔离：
  - **同一次运行内的相对比**（zoo 相对裸写法）——选型证据的**主体**
  - **绝对耗时**（每任务微秒数、每秒任务数）——标注"仅供同机同批次内部对照，不可跨运行比较"
- **理由**：CI runner 是共享虚拟机，绝对耗时会随同宿主上的其他负载漂移。跨运行引用绝对 µs 数字，一个字"你那是共享 runner"就足以否定整份报告。而**同机同一时刻的相对比**对这类漂移不敏感，因为漂移同时作用于对照双方。
- **代价**：报告无法给出"zoo 每任务 133 µs"这类便于记忆的对外数字。这是接受的取舍——可信度优先于易引用性。

### D7 · 调度语义维度走内部开关对照，不做横向对照

- **选**：只对 zoo 自身做开关对照——同一 workload 下语义全关，再逐个开启（优先级 / 超时 / 重试），差值即"语义单价"。裸写法不参与该维度。
- **理由**：优先级、超时、重试在裸写法中没有对应物，横向对照需要先给裸写法实现一份等价语义，而那份基线是"我们自己写的"——写得慢就是稻草人，写得快又难以证明它真的等价，自证风险只是换了个方向。
- **代价**：该维度只能回答"zoo 的语义值多少钱"，不能回答"比裸写法贵多少"。报告须在章节开头写明这一限制，避免读者误读为横向结论。

### D8 · 版本清单显式维护，不自动跟最新

- **选**：`matrix.yaml` 显式列出要测的框架版本；发版后由维护者追加一行。不自动跟踪 PyPI 最新版，也不自动跟踪 `dev` 分支。
- **理由**：自动跟版会让 zoo-bench 隐式依赖框架仓库的发布节奏，报告口径随框架发版被动变化，且"上一版数字复现不出来"这类问题极难定位。显式清单下，`zoo-bench run` 产出单版本快照，`zoo-bench compare v1 v2` 产出跨版本提升报告，二者共用同一套机制。
- **代价**：发版后需要一次人工追加。这是接受的成本。

### D9 · 报告由 zoo-bench 自建 Pages 承载，不做跨仓库写回

- **选**：报告与图表由 zoo-bench 的 GitHub Actions 构建并发布到该仓库自己的 Pages；框架仓库的 `README.md` 与 `docs/benchmark.md` 只各加一条链接。
- **理由**：跨仓库写回需要 PAT、会产生 bot commit 污染框架仓库历史、还要防循环触发，而收益仅为"少一次点击"。链接方案零写权限、零耦合。
- **代价**：框架 README 上不直接显示数字，读者需跳转。这是接受的取舍——独立仓库本身就意味着边界优先于便利。

### D10 · SDD 记录落在 zoo-bench 自己的 openspec/

- **选**：本变更的 proposal / design / specs / tasks 全部位于 zoo-bench 的 `openspec/`；框架仓库的 `openspec/` 不新增与 harness 相关的变更条目。
- **理由**：绝大多数实现工作发生在 zoo-bench，规格应与其代码同仓，避免"读规格要跨仓库"。框架侧的改动（`.gitignore` 一行、两条链接）在框架的 `docs/` 中说明即可，不足以支撑一个变更。
- **风险**：框架仓库的开发者可能不知道 zoo-bench 的存在。缓解：框架 README 的链接本身即是入口，且 `docs/benchmark.md` 会指向 zoo-bench。

## Risks / Trade-offs

**[报告自证——自己写的 harness 测自己的框架] → ** 这是最实质的风险：一份由 zoo 维护者编写、测量 zoo 性能的报告，读者有理由怀疑对照实现被故意写慢或口径被挑选。缓解：① 对照实现用最直白写法并公开源码；② 报告必须含"公开的不利数据"章节（D6、以及 spec 中的强制要求）；③ 适配器契约开放，任何人可提交自己的对照实现；④ 三条测量口径（D5）公开且可复核。**若报告只出现 zoo 获胜的档位，视为不合格产物。**

**[报告中的"框架开销"被误读为终端用户延迟] → ** 实测 `zoo-framework==0.6.0` 的 `Master` 运行循环是 `while True: self.waiter.execute_service(); await asyncio.sleep(1)`（`core/master.py:288-291`）——经 `Master` 的真实使用延迟被这 1 秒轮询支配，与被测的**派发原语**开销差三个数量级。若报告只写"框架开销 94 µs、占比 70.76%"而不声明被测层级，读者会把它读成"用户要等 133 µs"。缓解：本变更只驱动派发层（用户裁定，见 tasks 2.9），但**报告必须声明被测层级并说明它与终端用户所经验延迟的关系**——该要求已写成 `adapter-contract` 的一条场景，不是靠自觉。

**[发行包的版本标识自相矛盾] → ** 实测 `zoo-framework==0.6.0` 的 `zoo_framework.__version__` 是 `0.1.1-beta`，与发行元数据的 `0.6.0` 不一致（框架仓库的版本号在三个地方本就不统一，见其 CLAUDE.md）。若报告以 `__version__` 标注版本，报告与 matrix.yaml 就对不上。缓解：环境自述块以**发行元数据**（`importlib.metadata.version`）作为被测版本的真源，`__version__` 仅作附注，不作版本判据。

**[CI runner 是共享资源，绝对数字漂移] → ** 缓解：D6 的两类数字隔离是主要手段；此外每单元做足重复并报告离散度，使读者能判断哪一组数字稳定。

**[子进程隔离开销被误记为被测方案的开销] → ** 缓解：进程派生与依赖导入发生在计时区间之外（`setup` 之前）；任务中要求验证——给 `setup` 注入一段可测量的固定延迟后，测得的结果耗时不变。

**[语义单价的开关对照难以构造]"全关"基线 → ** 框架当前的语义由参数与 worker 类型共同决定，"全部关闭"未必存在一个干净的状态。缓解：任务中要求先枚举可开关的语义项并确认每一项存在"关闭"状态；若某项无法关闭，则在报告中剔除该项而非用近似状态代替。

**[`ProcessPoolExecutor` 档位的口径偏差] → ** 多进程与多线程的任务执行成本不可直接比较（跨进程要序列化入参与返回值）。缓解：该档位在报告中标注其额外成本来源，或限定为"同进程内并发模型"的参照而非 zoo 的直接竞争方案。

**[报告发布频率与新鲜度]** → ** 手动触发为主意味着报告可能滞后于框架版本。缓解：`matrix.yaml` 是显式清单（D8），滞后表现为"清单里没有新版本"这一可见状态，不会伪装成"已测过"。
