## 1. 仓库骨架与包结构

- [ ] 1.1 建立 `src/zoo_bench/` 包结构与 `pyproject.toml`（hatchling，`requires-python = ">=3.13"`）；验证：`pip install -e ".[dev]"` 成功，且 `python -c "import zoo_bench"` 无异常
- [ ] 1.2 声明 `zoo-framework` 为运行时依赖，且其版本由 `matrix.yaml` 决定而非固定字面量；验证：`pip install zoo-bench` 后 `pip show zoo-framework` 显示的版本等于 `matrix.yaml` 中当前选定的版本
- [ ] 1.3 按 design D3 把 `APScheduler` 放入默认依赖集、`Celery` 放入可选依赖集；验证：默认安装后 `import apscheduler` 成功而 `import celery` 失败；执行 `pip install -e ".[celery]"` 后 `import celery` 成功
- [ ] 1.4 建立 `matrix.yaml`，声明框架版本清单、并发度清单、执行体档位清单与默认适配器清单；验证：文件可被解析，且不包含硬编码在 Python 源码中的相同清单（`grep -rn "concurrency" src/` 只出现在读取配置的代码中）

## 2. 适配器契约与内置三档

- [ ] 2.1 按 design D2 定义契约 `setup` / `submit` / `drain` / `teardown`；验证：契约以 `typing.Protocol` 或抽象基类形式存在，且 `runner.py` 中不出现任何具体适配器名称
- [ ] 2.2 实现裸写法两档（每任务一线程、线程池）；验证：两档各自通过第 3.5 项的等价性验证
- [ ] 2.3 实现标准库其他并发模型两档（协程、多进程）；验证：两档各自通过第 3.5 项的等价性验证
- [ ] 2.4 实现 `APScheduler` 档位；验证：该档通过第 3.5 项的等价性验证
- [ ] 2.5 按 design D3 实现 `Celery` 档位并置于可选依赖门后；验证：未安装 `celery` 时导入该模块抛出可理解的错误而非 `ImportError` 裸抛，且该档不出现在默认矩阵结果中
- [ ] 2.6 按 design D3 在 `Celery` 档位的数据上标注"架构不同、不可直接对标"；验证：报告中该档位的条目带有该标注，且不参与交叉点结论的推导
- [ ] 2.7 按 design D4 实现测量单元的子进程隔离；验证：一轮运行多个适配器时，每个适配器运行在各自进程中（记录并比对进程标识）；某档故意抛异常时其余档仍完成
- [ ] 2.8 实现无源码修改的外部适配器登记机制；验证：在 `src/zoo_bench/` 之外新增一个实现契约的模块并登记后，它出现在测量结果中，且 `git diff --stat src/zoo_bench/runner.py src/zoo_bench/metrics.py src/zoo_bench/render/` 为空

## 3. 测量协议与 runner

- [ ] 3.1 实现执行体负载生成，按 `body_tiers_us` 调参；验证：实测各档执行体耗时随档位单调上升，且与设定值的偏差在容差内
- [ ] 3.2 按 design D5 在执行体内埋点记录自身耗时，并随结果回传；验证：原始数据中同时存在端到端耗时与该单元实测的执行体耗时
- [ ] 3.3 实现 warmup 与重复采样，输出去除预热数据后的分位数与离散度；验证：原始数据含至少两个分位数值与一项离散度指标，且预热轮次的数据不在其中
- [ ] 3.4 按 design D6 把结果分为"同运行内相对比"与"绝对耗时"两组；验证：结果结构中两组字段分离，读取任一组无需依赖另一组
- [ ] 3.5 实现适配器等价性验证（提交 N 个任务、断言全部执行且各执行一次）；验证：故意实现一个丢弃任务的适配器时验证失败，正常适配器通过
- [ ] 3.6 实现测量自检（执行体耗时与设定值的偏差、跨档位开销基线一致性）；验证：人为把某一档执行体的实际工作量设为设定值的两倍后自检失败，恢复后通过
- [ ] 3.7 按 D5 的验证要求确认框架开销不随执行体档位显著上升；验证：四档执行体下测得的框架开销落在同一量级，无单调显著上升
- [ ] 3.8 按 design D4 的计时区间要求确认子进程派生与依赖导入不计入耗时；验证：给某适配器的 `setup` 注入一段可测量的固定延迟，测得的结果耗时不变（该延迟落在计时区间之外）

## 4. 度量与报告渲染

- [ ] 4.1 实现原始数据的序列化与留档，路径按被测框架版本可寻址；验证：给定版本号可定位到对应数据文件，且同一份数据重新渲染结果一致
- [ ] 4.2 实现环境自述块的采集；验证：报告的环境章节含 CPU 型号与核数、OS 与内核、Python 版本、被测框架版本、commit sha、完整命令
- [ ] 4.3 实现 `zoo-bench render`，由原始数据产出 Markdown 与静态 SVG 图表；验证：不重新测量即可从既有数据产出一份完整报告
- [ ] 4.4 按 design D7 实现调度语义开关对照，并与横向对照在呈现上分离；验证：该维度章节开头声明其口径为内部开关对照、不与对照方案横向比较，且裸写法档位不出现在该章节中
- [ ] 4.5 按 design D7 的验证要求先枚举可开启的语义项并确认每项存在"关闭"状态；验证：报告中列出的每个语义项都有实测的关闭态数据；无法关闭的项被剔除而非用近似状态代替
- [ ] 4.6 实现结论摘要章节，给出交叉点或明示未观测到交叉点；验证：摘要中的交叉点可由报告内的档位数据推导
- [ ] 4.7 实现"公开的不利数据"章节；验证：当一个对照方案在某一档位上快于被测框架时，该档位出现在该章节且与有利档位同等显著
- [ ] 4.8 在报告中声明负载为替身而非真实 trace，并给出其构成；验证：报告的负载章节含该声明
- [ ] 4.9 按 design D3 与 Risks 中的口径要求在报告中标注偏差来源（多进程档位的序列化成本、`Celery` 的架构差异）；验证：这两处各自带有说明其成本来源或口径差异的标注
- [ ] 4.10 实现 `zoo-bench compare <v1> <v2>`，由留档数据产出跨版本变化对比；验证：对两个已留档版本执行后产出含各维度变化方向与幅度的结果；对未留档的版本执行时明确报告缺失而非产出充数结果

- [ ] 5.2 按 design D8 让 workflow 的版本清单来自 `matrix.yaml` 而非工作流内的硬编码；验证：工作流文件中不出现框架版本号字面量
